# 个人阶段小结：Ainspector 多模型代码审查评测

日期：2026-09-28 · 项目：Ainspector · 阶段：本地评测工具与 API 兼容性验证
记录归属：ayame2847 的个人学习分支。实现、实验整理和逐条评分采用 Codex 辅助完成；评分不是独立人类评委标注。

## 本阶段完成的工作

Ainspector 接收代码变更片段，调用语言模型生成代码审查意见。本阶段围绕“现有提示词与调用逻辑能否接入不同 API，以及返回的审查意见是否有依据”开展工作。

- 建立可选择服务商、案例和重复次数的本地评测工具，支持离线演练与真实调用，保存参数、源码哈希、模型回复、延迟及 token 用量。
- 设计 6 个虚构的 TypeScript patch，覆盖删除空值保护、删除管理员检查、循环越界、正确修复、纯格式修改和上下文不足。
- 完成 DeepSeek V4 Pro、Gemini 3.5 Flash Lite、MiniMax M3 各 6 个案例，共 18 条真实样本。
- 为 MiniMax M3 接入中国站 OpenAI 兼容接口并适配思考参数；补充完整 Markdown JSON 代码块解析及对应回归测试。
- 按同一评分尺度逐条检查缺陷命中、误报、修复可操作性和证据边界，记录具体判断依据。

验证结果：项目测试 54 项通过，评测工具自测 12 项通过。验证范围包括请求参数、返回内容解析和评测记录处理；不等同于 GitHub Bot 的端到端发布验证。

## 实验设计

每个模型对每个案例采样 1 次，直接调用项目 `Chat.codeReview`，不经过 Bot 的文件过滤、补丁长度限制、评论定位或发布流程。参考答案与评分标准预先保存在案例集中，不发送给模型。三个模型收到的逐例提示词哈希一致，可见采样参数均为 `temperature=1`、`top_p=1`、输出上限 4096 token、请求超时 120 秒。

DeepSeek 与 Gemini Lite 使用各服务的默认思考策略；MiniMax M3 关闭思考，依赖提示词生成 JSON，而另外两家还使用 `response_format=json_object`。MiniMax 批次采用了新增的 JSON 代码块兼容解析器。因此，本次比较反映各自的项目接入配置，不能视为统一推理预算或完全相同请求协议下的纯模型排名。每次实验的源文件哈希、运行参数和时间见 [experiments.json](experiments.json)。

|预设缺陷命中 / 缺陷样本|3/3|3/3|3/3|
|正常改动中的行为缺陷误报 / 样本|0/2|0/2|0/2|
|上下文不足案例的边界判断|通过|未通过|未通过|
|正常改动中的纯风格评论|0|0|1|

|请求总耗时中位数|7.162 秒|1.559 秒|2.979 秒|
|输入 token 总量|1,976|1,463|2,318|

|总 token|4,822|2,074|3,578|

技术成功表示返回内容能解析为规定的审查结构，不表示意见全部正确。正常改动误报只统计具体行为缺陷；风格意见单列，避免混淆“没有误报漏洞”和“没有额外审查噪声”。上下文不足案例单独评价，不纳入 3 个预设缺陷的命中率。

延迟为这 6 次顺序请求的总耗时中位数，各模型分批运行，受网络、缓存与服务负载影响。token 由各服务报告，分词方式不同；DeepSeek 的 2,237 个推理 token 已包含在输出总数内，不能重复相加。Gemini Lite 与 MiniMax 的响应没有提供推理 token 细分字段。

## 逐例发现

|案例|参考判断|三个模型的表现|
|---|---|---|
|删除空值检查|可选 `user` 为 `undefined` 时，访问其属性抛错|均命中。DeepSeek 和 MiniMax 提供明确修复；Gemini Lite 诊断准确，但未明确写出恢复检查等修复步骤。MiniMax 的空字符串兜底属于需求未证实的额外建议。|
|删除管理员检查|函数内授权保护消失，上游是否授权未知|均识别局部越权风险。Gemini Lite 明确以外部是否校验为条件；DeepSeek 和 MiniMax 的开头措辞偏确定，但后文提及调用层校验。不能据此断言整个系统一定可被越权。|
|循环多走一步|`values[values.length]` 为 `undefined`，累加得到 `NaN`|均命中并给出恢复 `<` 等可行修复。MiniMax 的补充说明却称当前空数组能返回 0；对修改后的 `<=` 循环，空数组也得到 `NaN`，该句是明显解释错误。|
|正确修复循环边界|修复旧的越界，不引入预设缺陷|均给出 LGTM，未将旧问题误判为新问题。|
|仅改变缩进|行为不变|DeepSeek 与 Gemini Lite 给出 LGTM；MiniMax 给出缩进建议并设 `lgtm=false`。该评论未声称行为缺陷，故不计漏洞误报，但“破坏项目规范”的断言缺少仓库格式配置证据。|
|timeout 从 1000 改成 1|未给出函数定义、单位与需求，无法定论|DeepSeek 要求确认单位并分情况讨论。Gemini Lite 与 MiniMax 均直接假定单位是毫秒，各计 1 项无依据缺陷断言。|

## 评分方法

评分由 Codex 阅读最终评论并对照参考答案完成，没有用关键词匹配代替语义判断。人工评分栏在此表示“逐条按标准审阅”，不代表独立的人类盲评。

- `hit_expected_issue`：三个缺陷案例填写 yes/no；正常改动和上下文不足案例填写 N/A。
- `false_positive_count`：缺乏代码证据支持的具体缺陷断言数；有条件的风险提示和纯风格建议不直接计入。
- `actionability_0_to_2`：0 为无法操作；1 为方向正确但修复不明确或依赖未核实假设；2 为原因具体且提出可行修复。无评论的 LGTM 记 N/A。
- 风格评论、解释错误和上下文边界另行标注，以保留单一分数无法表达的差别。

18 条样本均已填写评分依据，见 [scores.csv](scores.csv) 与 [grades.json](grades.json)。模型最终评论完整保存在 [records.json](records.json)，可逐条核对；这里不包含密钥、HTTP 认证头或模型的思考文本。

## 阶段结论与适用范围

本阶段验证了三个服务均能通过当前接入方式处理这组审查案例。简单缺陷检测上未观察到差异；区别主要体现在未知上下文下的判断、额外风格意见和解释准确性。Gemini Lite 在本批样本中延迟较低；DeepSeek 在唯一的上下文不足案例中表现更谨慎；MiniMax 识别了所有预设缺陷，但出现风格噪声及一处额外解释错误。

这些结果适合作为团队 project 的个人阶段记录：能够说明完成了什么、如何验证、观察到哪些差异。样本仅 6 个虚构短 patch、每题只采样一次，且没有独立人类盲评或真实 PR 端到端验证，因此不能作为正式模型排名或整体系统质量结论。
